# Terraform Provider for AWS Tagging

[![License](https://img.shields.io/badge/License-Apache_2.0-blue.svg)](LICENSE)

A custom Terraform provider designed to standardize AWS resource naming, tagging, and metadata enforcement across infrastructure stacks.

Built using the [Terraform Plugin Framework](https://developer.hashicorp.com/terraform/plugin/framework).

---

## Requirements

* [Terraform](https://www.terraform.io/downloads.html) >= 1.0
* [Go](https://golang.org/doc/install) >= 1.22 (for building/developing)

---

## Usage

### 1. Provider Configuration

Add the provider to your Terraform configuration:

```{hcl}
terraform {
  required_providers {
    awstagging = {
      source = "danieleborsaro/awstagging"
      version = "~> 0.1.0"
    }
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  alias = "detect"
  region = var.aws_provider_region
}

data "aws_caller_identity" "detect" {
  provider = aws.detect
}

data "aws_region" "detect" {
  provider = aws.detect
}

provider "awstagging" {
  account             = data.aws_caller_identity.detect.account_id
  accounts_coding     = var.accounts_coding
  compliance          = var.compliance
  cost_centre         = var.cost_centre
  infra_environment   = var.infra_environment
  owner               = var.owner
  project_name_long   = var.project_name_long
  project_name_short  = var.project_name_short
  region              = data.aws_region.detect.name
  resource_set_long   = var.resource_set_long
  resource_set_short  = var.resource_set_short
  role                = var.role
  terraform_module    = basename(abspath(path.root))
  terraform_workspace = terraform.workspace
}
```

### 2. Default Tags

Define default tags on the AWS provider. The `configuration` data source returns the tags every resource shares, without `Name` or `ResourceType`. The `awstagging` provider must read the account and region through `aws.detect`, because using the default AWS provider would create a cycle.

```{hcl}

data "awstagging_configuration" "this" {}

provider "aws" {
  region = var.aws_region

  # Automatically apply standardized default tags generated by the provider
  default_tags {
    tags = data.awstagging_configuration.this.tags
  }
}
```

Default tags are added to each resource's own tags, and the total still has to fit the resource's tag limit. The `configuration` data source leaves room for each resource's `Name` and `ResourceType` within the usual limit of 50. S3 objects allow only 10, which the default tags alone can exceed, so manage S3 objects through an AWS provider alias without `default_tags`:

```{hcl}
provider "aws" {
  alias  = "no_default_tags"
  region = var.aws_region
}

data "awstagging_aws_s3_object" "example" {}

resource "aws_s3_object" "example" {
  provider = aws.no_default_tags

  bucket = aws_s3_bucket.example.id
  key    = "example.txt"
  tags   = data.awstagging_aws_s3_object.example.tags
}
```

### 3. AWS Resources

Assign tags to AWS resources:

```{hcl}
data "awstagging_aws_autoscaling_group" "asg" {
  role_extend = "asg"

  custom_tags = {
    Environment = "Production"
  }

  custom_tags_verbatim = {
    Owner = "DevOps"
  }
}

resource "aws_autoscaling_group" "asg" {
  name = data.awstagging_aws_autoscaling_group.asg.name
  tags = data.awstagging_aws_autoscaling_group.asg.tags
  # ... other ASG parameters ...
}
```

## Tags

The provider generates AWS tags from the normalized resource configuration and the provider settings defined in [internal/shared/models.go](internal/shared/models.go). The actual assembly logic lives in [pkg/tagging/core/tagger.go](pkg/tagging/core/tagger.go).

### Tag Categories

The generator groups tags into four logical categories before flattening them into the final AWS tag set:

| Category | Generated keys | Source |
| --- | --- | --- |
| `Automation` | `TerraformModule`, `TerraformWorkspace` | Terraform runtime metadata |
| `Business` | `CostCentre`, `Owner`, `Project` | Billing / ownership / project metadata |
| `Security` | `Compliance` | Compliance metadata |
| `Environment` | `Account`, `AppEcosystem`, `AppEnvironment`, `Description`, `InfraEnvironment`, `ResourceSet`, `Role`, `ResourceType` | Environment and operational metadata |

> The `Name` tag is intentionally excluded from this generic table because it is treated specially by the naming layer and will be documented separately in its own section.

### Key Composition Rules

Tag keys are normalized and composed as follows:

1. The tag name is title-cased for consistency.
2. The category name is added when section-based key names are enabled.
3. A provider/company prefix is added to the final key.
4. Verbatim custom tags are injected as-is.

The resulting pattern is effectively:

- `CompanyShort:Section:TagKey`
- Example: `Foo:Automation:TerraformWorkspace`
- Example: `Foo:Custom:Environment`

For custom tags, the generator does one of the following:

- If sectioned names are enabled: `Foo:Custom:MyTag`
- Otherwise: the tag key is kept as provided

The implementation also strips empty values, removes reserved AWS-prefixed values, enforces the AWS tag limits, and truncates keys and values when necessary.

### Supported/Generated Tag Keys

| Category | Key | Example value |
| --- | --- | --- |
| Automation | `TerraformModule` | `payments-api` |
| Automation | `TerraformWorkspace` | `prod` |
| Business | `CostCentre` | `12345` |
| Business | `Owner` | `platform-team` |
| Business | `Project` | `Payments` |
| Security | `Compliance` | `pci` |
| Environment | `Account` | `123456789012` |
| Environment | `AppEcosystem` | `Payments` |

| Environment | `ResourceSet` | `PaymentsRoot` |
| Environment | `Role` | `Database` |
| Environment | `ResourceType` | `aws_autoscaling_group` |

### Custom Tags

The provider supports two custom tag inputs:

| Input | Behavior |
| --- | --- |
| `custom_tags` | Normalized and sectioned by the provider naming policy |
| `custom_tags_verbatim` | Added as-is without the standard section or company prefixing rules |

These are merged with the standard generated tags, and empty values are ignored before the final tag map is emitted.

### AWS Compatibility Rules

The tag builder also applies AWS constraints during generation:

- key length is capped at 127 characters
- value length is capped at 255 characters
- keys and values starting with `aws:`, in any case, get a `:` prefix. If both `aws:x` and `:aws:x` are set, the key as written (`:aws:x`) wins and the other is dropped
- over the target resource type's tag limit, tags are kept in this order and the rest are dropped with a warning: `Name`, generated tags, custom tags, verbatim tags, alphabetically within each
- any tag with an empty value is dropped before final emission

This means the effective output is a normalized, provider-scoped tag map that remains AWS-safe while preserving the business, security, and operational metadata expected by the platform.

## Resource Names

The Name tag is handled as a special-case output of the naming pipeline rather than as a normal generated tag in the generic tag map. The tagging flow in [pkg/tagging/core/tagger.go](pkg/tagging/core/tagger.go) deliberately preserves Name as a standalone key and does not apply the usual company-prefix/section prefixing to it, while the actual value is computed by the resource naming engine in [pkg/tagging/core/namer.go](pkg/tagging/core/namer.go).

The naming strategy is based on a resource-specific component model:

* Each AWS resource declares the set of name components it supports and the constraints it must obey.
* The namer selects the relevant components for that resource, such as account code, environment, project, region, resource set, role, and type.
* These components are assembled in the order defined by the resource metadata, then sanitized to match AWS naming constraints.
* When uniqueness is required, a deterministic hash suffix is appended to keep names stable and collision-safe.

This logic is centralized in [pkg/tagging/core/resources.go](pkg/tagging/core/resources.go) and [pkg/tagging/core/namer.go](pkg/tagging/core/namer.go), while resource-specific variations are implemented under [pkg/tagging/aws](pkg/tagging/aws). For example:

* KMS aliases require special handling
* CloudWatch log streams use a different separator
* target groups get an application-environment-aware prefix
*some resources enforce lowercase-only names or other AWS-specific constraints

The result is that the [Name](pkg/tagging/shared/data.go) tag is not a free-form label; it is the provider’s canonical resource name, computed from the platform’s standard naming vocabulary and then adapted to each AWS resource convention. In practice, the value can be used as the actual resource name in Terraform or in downstream AWS resource creation flows, while the tag key remains simply Name.

In other words, the [Name](pkg/tagging/shared/data.go) tag is the “standardized resource identity” output, while the other tags express metadata about ownership, compliance, environment, and automation. The detailed naming logic for each individual AWS resource type remains in the resource definitions under pkg/tagging/aws, and that directory is the right reference point when documenting resource-specific naming behavior.

## Local Development

### Prerequisites

Tooling is managed via asdf (optional, but recommended):

* [asdf](https://asdf-vm.com/guide/getting-started.html) >= v0.11.1

```{bash}
asdf install
```

### Building The Provider

1. Clone the repository:

```{bash}
git clone [https://github.com/danieleborsaro/terraform-provider-awstagging.git](https://github.com/danieleborsaro/terraform-provider-awstagging.git)
cd terraform-provider-awstagging
```

2. Compile the binary locally:

```{bash}
go install .
```

### Local Testing Eith Terraform

To test local changes against a Terraform configuration without publishing to a registry, configure a development override in ~/.terraformrc:

```{txt}
provider_installation {
   dev_overrides {
    "localdev/foo/awstagging" = "$GOPATH/go/bin"
  }

  filesystem_mirror {
    path    = "/home/daniele/.terraform.d/plugins"
    include = [
	    "github.com/danieleborsaro/*"
    ]

    exclude = [
      "registry.terraform.io/*/*"
    ]
  }
  direct {
    exclude = [
	    "github.com/danieleborsaro/*"
    ]

    include = [
      "registry.terraform.io/*/*"
    ]
  }
}


```

Local bilds are read from `$GOPATH/bin`. Snapshot releases are instead to be staged in a local plugin directory:

```{bash}
mkdir -p ~/.terraform.d/plugins/github.com/danieleborsaro/awstagging
```

*Note*: When using dev_overrides, Terraform will issue a warning indicating that local binaries are in use.

## Releasing

Releases are managed via GoReleaser.


### Local Snapshot Build

To verify cross-compilation and packaging without publishing:

```{bash}
goreleaser release --snapshot --clean
mkdir -p ~/.terraform.d/plugins/github.com/danieleborsaro/awstagging/0.0.0-SNAPSHOT-64bf0c4/darwin_arm64
cp dist/terraform-provider-awstagging_linux_amd64_v1/terraform-provider-awstagging_v0.0.0-SNAPSHOT-64bf0c4 ~/.terraform.d/plugins/github.com/danieleborsaro/awstagging/0.0.0-SNAPSHOT-64bf0c4/darwin_arm64
```

### Publishing a Release

Official releases are generated automatically via GitHub Actions when a semantic tag is pushed:

```{bash}
git tag -a v0.1.0 -m "Release v0.1.0"
git push origin v0.1.0
```
